# TripMaster 重新设计方案

## 1. 产品重新定位

TripMaster 不再定位成：

“保存景点、填写行程、记录预算的旅行管理系统”

而是：

**一个帮助用户快速完成「多城市 → 每日景点 → 城际/市内交通 → 时间 → 预算」规划的地图旅行工作台。**

核心用户不是“不知道去哪里”的人，而是：

> 我大概已经知道想去北京、南京、苏州和上海，现在需要快速把路线、时间和预算组织清楚。

因此核心价值应该是：

**少录入、少跳页面、地图驱动、自动计算、随时调整。**

---

# 2. 最核心的产品模型

现在的数据结构主要是：

POI → Itinerary → Budget

这会导致行程、地点、交通和预算互相割裂。

新版应该变成：

```text
Trip 一次旅行
│
├── CityStay 城市停留
│   ├── Day 每一天
│   │   ├── Stop 景点/酒店/餐厅/车站
│   │   ├── Segment 交通
│   │   ├── Stop
│   │   ├── Segment
│   │   └── Stop
│   │
│   └── Day
│
├── IntercitySegment 城际交通
│
└── CityStay
```

### Trip

例如：

```text
国庆华东旅行
2026/10/1 - 2026/10/7

北京
↓
南京
↓
苏州
↓
上海
```

### CityStay

表示：

```text
南京
10月3日 → 10月4日
住宿：新街口附近
```

### Day

表示当天的完整安排：

```text
10月3日 南京

09:00 中山陵
↓ 公交 32 min ¥2

12:30 新街口
↓ 地铁 18 min ¥3

15:00 南京博物院
```

### Stop

Stop 不只是“景点”。

可以是：

```text
景点
酒店
餐厅
机场
火车站
购物
自定义地点
```

### Segment

这是新版最重要的数据对象。

所有交通统一表示为：

```text
起点 → 终点

方式
时间
费用
路线
备注
```

所以：

```text
故宫 → 天坛
```

和：

```text
北京 → 南京
```

本质上都是 Segment。

只是前者是市内交通，后者是城际交通。

```text
北京

南京
↓
苏州
↓

```

可以先规划后补。

# 6. 景点添加流程重新设计

现在：

```text
地点管理
↓
搜索
↓
收藏
↓
行程规划
↓
再次添加
```

全部删除。

新版：

用户进入：

```text
北京 · 10月1日
```

地图顶部直接：

```text
🔍 搜索景点、餐厅、酒店、车站……
```

搜索：

```text
故宫
```

地图直接显示结果。

点击地图上的故宫：

```text
故宫博物院

开放时间
地址
预计游玩 3h

[加入 10月1日]
[收藏]
```

点击一次：

**加入 10月1日**

完成。

收藏只是辅助功能，不再是前置步骤。

# 7. 支持地图直接选点

除了搜索，还应该支持：

```text
地图点击 POI
       ↓
加入当天行程
```

例如用户在地图上看到：

```text
景山公园
```

直接点击：

```text
+ 加入今天
```

而不用搜索一次。

这是地图旅行工具和普通表单工具体验差异最大的地方之一。

---

# 8. 一天的行程不再使用“表单编辑”

现在一个景点下面需要填写：

```text
描述
预算
交通方式
交通时间
交通费用
交通说明
```

太重。

新版直接显示成：

```text
☰  09:00
① 故宫
   预计游玩 3h

   ↓ 地铁
     37 min · ¥5
     [更换]

☰  13:00
② 天坛
   预计游玩 2h

   ↓ 打车
     24 min · 约 ¥32

☰  16:00
③ 三里屯
```

用户看到的是“旅行”。

而不是数据库字段。

# 9. 拖动就是重新规划

用户直接拖动：

```text
故宫
天坛
颐和园
```

变成：

```text
颐和园
故宫
天坛
```

TripMaster 自动重新计算：

```text
路线
交通方式
预计时间
当天交通费用
到达时间
地图线路
```

不再需要：

```text
⬆

```

按钮。

# 10. 增加“优化路线”

这是非常适合 TripMaster 的核心功能。

例如：

```text
今天已选择：

故宫
颐和园
天坛
798
```

用户点击：

**优化顺序**

系统根据地理位置和交通时间建议：

```text
颐和园
↓
故宫
↓
天坛
↓
798
```

但有一个很重要的设计：

支持：

🔒 锁定地点

例如：

```text
故宫
预约 10:00
🔒
```

路线优化不能移动这个地点。

这样自动规划才不会和真实预约冲突。

# 12. 城际旅行单独强化

现在 TripMaster 最大的缺失之一就是：

**没有真正建立“城市之间”的旅行结构。**

新版首页地图应该先体现：

```text
北京
│
│ 高铁 3h31min
│ ¥443
↓
南京
│
│ 高铁 1h04min
│ ¥99
↓
苏州
│
│ 高铁 28min
│ ¥40
↓
上海
```

用户点击：

```text
北京 → 南京
```

打开交通卡片：

```text
北京 → 南京

○ 高铁
○ 飞机
○ 自驾
○ 其他

10月3日

出发：
北京南站

预计：
```

```text

```

# 13. 酒店应该参与路线规划

酒店不是普通备注。

它应该是 CityStay 的“基地”。

例如：

```text
北京

住宿
北京王府井某酒店
```

当天可以选择：

```text
从酒店出发
```

那么路线就是：

```text
酒店
↓
故宫
↓
天坛
↓
三里屯
↓
酒店
```

实际旅行非常常见。

**行程即预算。**

例如：

```text
华东旅行

预计总预算
¥5280
```

点击展开：

```text

城市间
北京 → 南京       ¥443
南京 → 苏州        ¥99
苏州 → 上海        ¥40

城市内

南京               ¥400
```

**预算自动变化。**

彻底删除：

> 从行程同步

这个按钮。

---

# 15. 金额分成三种状态

预算可以进一步设计得更实用。

每一项允许：

```text
预计 ¥450
```

预订以后：

```text
已确认 ¥443
```

旅行过程中：

```text
实际 ¥443
```

所以整个 Trip 可以看到：

```text
预计预算
¥5280

已确认
¥3920

实际支出
¥1280
```

这样 TripMaster 既适合规划前，也适合旅行中使用。

# 16. 备忘录也不要单独做一级页面

现在的 Markdown Memo 功能可以保留，但放回旅行内部。

例如：

```text
旅行资料

✓ 故宫预约
✓ 酒店订单
✓ 高铁票

备注
护照
相机充电器
学生证
```

甚至支持某一项自己的备注：

```text
故宫

预约码：
XXXX

备注：
从东华门进入
```

不需要整个软件单独一个“备忘录管理”。

# 17. 搜索和“想去清单”分开

可以保留原来的 POI 收藏能力，但是重新定位。

叫：

**想去**

例如：

```text
北京 · 想去

☆ 故宫
☆ 颐和园
☆ 环球影城
☆ 798
☆ 天坛
```

这些地方还没有安排具体日期。

用户可以：

```text
拖到 Day 1
拖到 Day 2
```

所以：

```text
想去清单
```

是暂存区。

而不是规划行程的必经流程。

---

# 18. 自动化和人工操作边界

TripMaster 不应该什么都自动安排。

用户负责：

```text
想去哪
哪天去
哪些安排不能动
选哪种交通
预算偏好
```

系统负责：

```text
距离
路线
交通时间
地图绘制
交通费用估计
时间冲突
预算统计
路线优化
```

这比“AI 自动给你生成一份旅行攻略”更稳定，也更符合工具定位。

AI以后可以加，但只是辅助能力。

例如：

> “把故宫、天坛、颐和园安排进两天，不要太赶。”

AI负责修改已有 Trip 数据。

而不是把整个产品变成聊天机器人。



# 22. 云端架构也可以简化

不建议继续维护：

```text
Express
+
自己管理用户
+
MySQL
+
JWT
```

除非以后真的需要复杂后端。

前期可以采用：

```text
静态前端
       ↓
可选云同步层
       ↓
PostgreSQL/BaaS
```

这样：

本地部署非常简单。

云端部署也非常简单。

而且核心规划功能即使服务器挂了仍然可以使用。

# 23. 数据格式也重新设计

TripMaster 应该有自己的旅行文件，例如：

```text
my-trip.tripmaster
```

本质可以仍然是 JSON。

结构类似：

```text
Trip
├── metadata
├── cities
├── days
├── stops
├── segments
├── expenses
└── notes
```

支持：

```text
导出旅行
导入旅行
```

以后不同版本通过：

```text
schemaVersion
```

迁移。

这比把 POI、预算、Memo 各自导入后端可靠很多。

# 28. 产品最终应该是什么感觉

我希望新版打开以后更像：

**Google Maps + 时间线 + 简化版 Notion 行程表**

而不是：

**旅游 CRUD 后台管理系统。**

整个软件应该围绕三个问题展开：

> 今天去哪？

> 怎么过去？

> 总共要花多少钱？

只要 TripMaster 把这三个问题处理得特别顺，它就已经是一个很好用的旅行规划工具。
